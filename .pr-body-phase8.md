# Phase 8 — `earnings_lookup`: a read-only earnings observation, without a second rulebook

**Branch:** `phase8-earnings-lookup`
**Tool:** `earnings_lookup` (local, gateway-side, read-only)

## What it answers

One `SELECT` on `public.stock_fundamentals` — `symbol`, `next_earnings_date`,
`event_calendar_as_of_date` — read as `xang_ro` over the existing
`XANG_DB_DSN`. No new grants, no writes, no Yahoo call.

```json
{
  "symbol": "AAPL",
  "next_earnings_date": "2026-11-02",
  "event_calendar_as_of_date": "2026-10-22",
  "source": "xang_yahoo_calendar",
  "freshness_status": "ok",
  "date_confirmation": "unknown",
  "available": true,
  "reasons": ["date_confirmation_unrecorded"],
  "observation_age_days": 2,
  "event_calendar_max_age_days": 14,
  "event_calendar_producer_refresh_after_days": 7,
  "event_calendar_future_tolerance_days": 3,
  "generated_at": "2026-10-25T06:58:11.412Z"
}
```

## The reuse decision (and why it is not a copy)

The freshness rule already exists in `app.services.yahoo_earnings_calendar`
(14 days observation age, 7 days producer refresh, 3 days future tolerance).
That module ships in the backend image and — exactly like the Phase 7 calendar
service — is copied into this image at build time
(`COPY --from=xang-backend /app/app /opt/xang_backend/app`).

`earnings.py` **imports** it, the same way `calendar.py` imports
`MarketCalendarService`:

- `is_event_calendar_observation_fresh()` decides fresh vs. not fresh.
- `persisted_next_earnings_date()` decides whether a stored date is evidence.
- the three constants are read from the module and repeated in the answer, so a
  consumer can see which window produced the verdict.

No threshold is written twice. The guard against silent drift is a test:
`TestRulesAreInjected` injects a stub with a **5-day** window and a **30-day**
window and asserts the verdict follows the injected rule. If anyone ever
re-derives `14` inside the gateway, that test fails.

When the backend tree cannot be imported, the tool answers
`freshness_rules_unavailable` (fail closed) rather than falling back to a local
number.

## States

| `freshness_status` | When | `available` |
|---|---|---|
| `ok` | observation inside the canonical window and the stored date is usable | true |
| `stale` | observation older than `EVENT_CALENDAR_MAX_AGE_DAYS` | false |
| `invalid` | unreadable/future observation date, past earnings date, unreadable date, bad symbol, missing rules | false |
| `unknown` | no DSN, database error, no row, missing observation date | false |

`available` is true only when the observation is usable **as evidence** — a
fresh observation that says "nothing upcoming" counts (that is a fact), a stale
one never does.

Reasons are machine-readable codes: `invalid_symbol`, `database_not_configured`,
`database_unavailable`, `symbol_not_found`, `observation_date_missing`,
`observation_date_invalid`, `observation_stale`, `observation_date_in_future`,
`earnings_date_missing`, `earnings_date_unreadable`, `earnings_date_in_past`,
`no_upcoming_earnings_date`, `date_confirmation_unrecorded`,
`freshness_rules_unavailable`.

## What it refuses

- **No guessed confirmation.** `stock_fundamentals` stores no confirmation
  proof, so `date_confirmation` is always `unknown`. `confirmed` is never
  emitted; `estimated` would be an assertion about the provider that the data
  cannot support.
- **No filling of gaps.** A missing row, a missing observation date or a NULL
  `next_earnings_date` stays missing and is named.
- **No writes.** The statement is a single parameterised `SELECT … WHERE symbol
  = %s LIMIT 1`; the connection is switched to `read_only` when the driver
  supports it. There is no code path that issues anything else.
- **No leaked driver text.** A database exception is logged by type and
  answered as `database_unavailable`; the message never reaches the caller.

## Wiring

- `LOCAL_TOOLS` gains `earnings_lookup` (so it is in the allowlist surface).
- `tools/list` advertises it next to `market_calendar_status`.
- `tools/call` answers it locally — no backend round trip (asserted: a
  `FakeTransport` with zero responses and any passthrough would explode).
- A missing `symbol` argument is JSON-RPC `-32602`; an invalid symbol is a
  *fact* (`invalid_symbol`), not a protocol error.
- Auth, backend allowlist and every existing tool are untouched.

## Tests

`tests/test_gateway_earnings.py` — 31 tests:

- symbol normalisation, invalid symbols, SQL-injection attempt (asserts the
  database is never touched and the SQL contains `%s`, not the value)
- fresh future date, fresh observation without a date, missing row, stale
  observation, unreadable observation date, missing observation date, past
  earnings date, future observation beyond tolerance
- database error → `unknown`, no driver text in the answer
- no DSN → `unknown` / `database_not_configured`
- missing rules → fail closed
- query is parameterised and the connection is read-only
- injected-window guard (5 days / 30 days)
- canonical reuse against the real module (15-day matrix, future tolerance),
  skipped when the backend tree is absent — as in CI
- route: `tools/list`, local `tools/call`, protocol error, fact-level invalid
  symbol, `market_calendar_status` still answering, unknown tool still rejected

Existing assertions that hardcoded "12 + 1 tools" now use
`len(LOCAL_TOOLS)`, so adding a local tool cannot break them silently — the
count is still asserted, just derived.

```
local (backend tree present):  107 passed, 1 skipped
CI simulation (no tree):        99 passed, 9 skipped
ruff:                           clean
```

The skipped tests are the ones that deliberately require the canonical backend
tree; they run in the image build and on any host that ships it.

## Not touched

Backend tools, auth module, enrichment, `market_calendar_status`, Docker
configuration, Hermes, XANG Long/Short logic. Hermes watchlist scanner stays
`enabled=False`. No deployment, no merge.
